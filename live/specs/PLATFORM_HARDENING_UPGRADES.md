# Platform Hardening Upgrades

Purpose: define the pre-paper-trading validity upgrades that must sit around the
existing flat-file live runtime. This is an implementation checklist, not a new
strategy spec.

## 1. Point-In-Time Causality

Every feature used by a strategy should be represented, when practical, as a
`FeatureSnapshot`:

- `event_ts`: when the source market/account event happened.
- `available_at_ts`: when the strategy could have known it.
- `current_bar_ts`: the bar-close timestamp being evaluated.
- `feature_name`, `source`, `value_ref`, `metadata_json`: audit context.

The invariant is:

```text
event_ts <= available_at_ts <= current_bar_ts
```

`CausalityGuard` enforces this invariant and records `CausalViolation` rows. It
also checks non-reduce order intents with explicit `live_after_ts` values.

Modes:

- `audit`: record violations and continue. Use for research and legacy replays.
- `strict`: block new non-reduce orders on violations. Use for paper/live
  candidates. Reduce-only protective exits remain allowed.

`paper_eligible` promotion requires a qualifying run with
`causality_mode = "strict"`.

`StrategyActions.causal_features`. This does not change trade logic; it adds an
audit trail around the features already being used.

## 2. Replay Manifests

Every major replay should write:

- `run_manifest.json`
- `run_manifest.sha256`

Required fields:

- run id, command, cwd, Python version, platform
- git commit, dirty flag, short status
- causality mode
- strategy config
- broker realism config
- data input paths and hashes
- output artifact paths and hashes
- extra run-specific metadata

The manifest is the source of truth for reproducing a result months later.
Reports and promotion status should be generated from manifests and audit files,
not hand-entered metrics.

## 3. Promotion Status

`promotion_status.json` is generated by `live/promotion.py` from artifacts:

- `run_manifest.json`
- `summary.csv`
- `execution_scrutiny.csv`
- `causality_violations.csv` or `events/causality_violations.jsonl`
- null-replay summaries
- DSR ledger
- campaign-level PSR/DSR outputs

Promotion states:

```text
research -> broker_like -> hardened_realism -> null_tested
-> causality_passed -> tick_escalated -> paper_eligible
```

`null_tested` and `causality_passed` should use campaign-level inference where
campaign P&L exists. Daily Sharpe/Sortino remains a secondary exhibit.

Example blocking reasons:

- `missing_null_results`
- `tick_escalation_required`
- `causality_violations>0`
- `causality_mode_not_strict`
- `missing_campaign_dsr`
- `missing_dsr_ledger`

## 5. Execution Scrutiny

Applicable replay families should emit `execution_scrutiny.csv`.

Classification values:

- `OK`: bar-level evidence is sufficient for the replay assumption.
- `NEEDS_TICK`: 1m bars are insufficient; this is not necessarily a violation.
- `VIOLATION_RISK`: impossible or causally suspect sequence; must correspond to
  a `CausalViolation`.

Required report rollups:

- scrutiny rows / total trades
- `OK`, `NEEDS_TICK`, `VIOLATION_RISK` counts
- tick-critical percentage
- unresolved tick manifest rows

## 6. Acceptance Criteria

Before a strategy can be called paper-eligible:

- strict causality run exists
- `causality_violations` count is zero
- replay manifest exists and hashes outputs
- hardened realism config is recorded
- null-family result exists with adequate seeds
- campaign-level PSR/DSR output exists when campaign P&L exists
- execution scrutiny has no unresolved `VIOLATION_RISK`
- unresolved `NEEDS_TICK` rows are reviewed or explicitly accepted in the
  promotion report
